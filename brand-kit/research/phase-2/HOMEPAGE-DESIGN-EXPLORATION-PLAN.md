# Mez Systems homepage-led design exploration

Status: Hero 03 direction approved with mobile revision; homepage paused for Living Core systemization
Primary content source: `mez.systems - Homepage` in Notion
Production authority: none until the defined human and transfer gates pass

## End goal

Create a recognisable Mez Systems design language that can generate high-quality websites, sales pages, product shelves, checkout and bundle surfaces, ads, emails, reports, decks, social assets, Figma libraries, and coded components without losing identity when a logo is removed.

The system is built for LLM use first, but the human receiver determines whether the output is clear, premium, coherent and recognisably Mez. The system therefore needs both machine-readable constraints and a small set of strong visual examples.

## Correct product model

Mez Systems sells installable operating systems, context systems, Claude Code environments, Notion systems, templates, playbooks and bundles. The website does not need an invented SaaS dashboard to prove the brand. Product proof can use real screenshots, carefully redacted operating artefacts, mockups, recordings, diagrams, files and installable-system packaging.

The primary design problem is marketing and commerce:

- homepage and hero systems;
- product and product-family cards;
- proof and mechanism sections;
- ethos and belief sections;
- individual-product sales pages;
- one-time purchase, multi-product selection and bundle surfaces;
- customer proof and trust;
- navigation, footer and responsive behaviour;
- channel transfer into ads, email, decks, reports and social.

## Source mechanisms to translate

### From Notion

- low-density orientation followed by higher-density inspection;
- one strong thought, one clarifying sentence, paired actions and one literal proof object;
- semantic spacing based on content relationships rather than uniform gaps;
- shared family grammar with products differentiated by job and proof object;
- calm neutral framing with small moments of expression;
- product, marketing, documentation and templates using the same nouns and objects.

### From ElevenLabs

- product discovery embedded in the opening composition;
- an expressive product object that carries energy without colouring the whole page;
- distinct product territories held by one parent system;
- strong mobile compression that retains the core identity;
- proof placed at the point of the claim;
- variation in media and composition based on product job.

### Mez translation boundary

Do not copy Notion characters, block styling, exact black-and-white composition, inline software capsule or product frames. Do not copy ElevenLabs spheres, audio controls, voice objects, platform palette allocation, Chladni graphics or page composition.

Translate the underlying mechanisms into Mez's own recurring behaviour: intelligence sources can change while an owned operating layer remains. The relationship between interchangeable tools and the persistent system is the candidate recognition grammar.

## Superseded sequence preserved for audit

### Phase A: website foundation studio

Build four polished homepage foundation studies. Each study must use the same copy and include the same representative modules:

1. global navigation;
2. full hero and visual mechanism;
3. ethos or belief section;
4. AI OS featured product;
5. coming-soon product shelf;
6. one-time purchase or bundle composition;
7. final CTA and footer behaviour;
8. mobile recomposition.

The studies are not named through vague brand adjectives. Each declares exact candidate values for type, surface, radius, spacing, gradient behaviour, depth and recognition mechanism.

### Phase B: short human annotation

Olli reviews each study full-size. The interface captures:

- overall: `promising`, `useful details`, or `not Mez`;
- per module: `keep`, `change`, `too much`, `too plain`, or `not Mez`;
- foundation reactions for typography, colour, radius, spacing, composition and gradient use;
- an optional note.

No forced winner. No broad adjective scoring. Estimated human time: 10 to 15 minutes for the first four studies.

### Phase C: coherent synthesis

Build one synthesis from retained behaviours. Do not average the studies. Select one dominant grammar and explicitly list donor behaviours, rejected behaviours and unresolved variables.

The synthesis must pass three recognition checks:

1. logo removed;
2. gradient removed;
3. grayscale thumbnail.

It should still feel like one authored system through composition, spacing, shape, hierarchy and the owned-layer behaviour.

### Phase D: one complete homepage

Apply the synthesis to the complete Notion section map. Use real or intentionally redacted proof assets, not invented software UI. Build desktop and mobile with production-level copy rhythm, interaction and accessibility.

### Phase E: component and token extraction

Extract only proven rules:

- semantic type roles and responsive scale;
- surface and contrast roles;
- spacing and adjacency rules;
- shape and radius grammar;
- buttons and links;
- product, purchase and bundle cards;
- proof frames and annotations;
- navigation and footer;
- gradient placement rules;
- motion roles;
- page-section composition contracts.

Encode them in CSS variables, JSON tokens, component contracts, visual examples, allowed variants, forbidden combinations and automated checks.

### Phase F: commerce proof

Test the system on:

- one live product purchase;
- two-product bundle;
- multi-product shelf with mixed live and coming-soon states;
- order summary;
- checkout handoff;
- success, cancellation and refund-support states.

### Phase G: cross-channel transfer

Use the approved homepage language to create golden examples for one ad set, lifecycle email, report spread, deck opening, social post, mobile page and small-format identity. Each channel changes density and composition while retaining the same system behaviour.

### Phase H: Figma and distribution

After code has established the working grammar:

1. create Figma variables from approved tokens;
2. build Figma components from the proven code contracts;
3. map code and Figma through Code Connect or an equivalent parity layer;
4. package assets, templates, examples, schemas and validators;
5. distribute a versioned team package and an LLM context pack;
6. test that another human and another LLM can produce a new-context asset without hidden project knowledge.

Code comes before Figma during exploration because responsive behaviour and rapid full-page variation are faster to test in the browser. Figma becomes authoritative for shared design authoring only after the grammar is approved and mapped back to tested code.

## Quality gates

An artefact does not reach Olli because it exists. Before human review it must pass:

- copy-source check;
- system-variable declaration;
- desktop and mobile visual QA;
- no horizontal overflow;
- accessible contrast and focus;
- source-signature review;
- internal visual-quality review;
- screenshot review at full size and thumbnail size;
- proof that all feedback controls refer to visible, specific design decisions.

## Stop conditions

- Stop if the work can be described only through adjectives rather than visible rules.
- Stop if the gradients are the only recognisable behaviour.
- Stop if every section becomes the same rounded card.
- Stop if visual variety comes from breaking the chosen system rather than applying semantic rules.
- Stop if the review asks Olli to approve low-fidelity or incomplete work.
- Stop if a source brand is recognisable in a logo-free thumbnail.
- Stop before production token promotion when human approval or migration analysis is missing.
